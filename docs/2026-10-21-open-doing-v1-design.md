# Open Doing v1 功能设计

日期：2026-10-21
状态：已定稿

## 1. 背景与目标

Open Doing 是一个项目任务进度管理系统，要解决三个问题：

1. **个人任务理不清**——每个人需要一处管理自己所有的待办。
2. **团队进度未同步**——成员之间看不到彼此在做什么。
3. **上级不清楚工作情况**——主管需要了解项目风险与每个人的工作负载，但不应依赖额外填报。

### 目标

- 每个用户默认拥有个人空间，并可创建/加入多个团队空间。
- 团队 → 项目 → 任务的层级结构，任务支持子任务与评论。
- 任务进度自动可算，项目/团队进度自底向上聚合，无需手工汇报。
- 主管在团队概览页只读地掌握风险、进度与成员负载。

### 非目标（v1 明确不做）

- 任务优先级、标签
- 任务/项目的操作动态流水（谁在什么时候改了什么）——后续版本再做
- 密码找回
- 邮件通知（只做系统内通知）
- 第三方登录（GitHub/Google 等）
- 收集邮箱（注册只有用户名和密码）
- 催办、审批等管理动作（主管在系统内只看不动）

### 反目标（即使技术上可行也算失败）

- 为了汇报而要求成员手工填写进度、日报等额外数据。
- 权限模型复杂到需要专门培训。

## 2. 空间层级

```
用户（注册即拥有个人空间）
├── 个人空间
│   ├── 个人项目（可创建多个）
│   │   └── 任务
│   │       ├── 子任务
│   │       └── 评论（自我备注）
│   └── 个人任务（不归属任何项目）
└── 团队空间（可创建多个，也可加入多个）
    └── 项目
        └── 任务
            ├── 子任务
            └── 评论
```

- 个人空间不可删除、不可邀请他人、对他人不可见。
- 个人空间内可以创建**个人项目**来组织任务，也可以保留不属于任何项目的零散个人任务；两者都只属于本人。
- 一个用户可以同时是多个团队的成员。

## 3. 账号体系

- 注册：**用户名 + 密码**，不收集邮箱。用户名由用户自己起，用于登录，全局唯一；v1 中用户名同时作为显示名（责任人选择器、概览页等处直接显示用户名）。用户名命名规则（长度、允许字符）由实现确定。
- 密码登录，采用安全的 cookie session（具体认证库/自管方案由实现选择）。
- **UID**：注册时由系统内部生成，全局唯一，格式为 `doing_xxxx`（`doing_` 前缀 + 随机串；长度与字符集由实现确定，必须保证唯一且不易枚举）。UID 是邀请成员时使用的身份标识，不是登录名。
- v1 不做密码找回。

## 4. 团队与邀请

### 团队

- 任意用户可创建团队，创建者自动成为 owner。
- 团队信息至少包括：名称、成员列表。
- owner/admin 可修改团队设置（v1 主要是团队名称）。

### 邀请流程

1. owner/admin 输入对方的 UID（`doing_xxxx`）发起邀请。
2. **被邀请的 UID 必须属于已注册用户**；UID 不存在时提示无效。（实现决定：不做"预邀请未注册用户"）
3. 被邀请方登录后，在"待处理邀请"中看到邀请，可以**接受或拒绝**。
4. 接受后成为团队 member；拒绝则邀请标记为失效。
5. 待处理邀请可由 owner/admin 撤销。
6. 邀请发出、接受、拒绝、撤销时产生系统通知。

实现约定（实现决定）：v1 邀请不设有效期，pending 状态保持到对方响应或被撤销；不允许对同一人重复发起 pending 邀请。

## 5. 角色与权限

三种团队角色：**owner / admin / member**。

| 操作 | owner | admin | member |
|---|---|---|---|
| 修改团队设置（改名） | ✅ | ✅ | ❌ |
| 邀请成员 / 撤销邀请 | ✅ | ✅ | ❌ |
| 移除成员 | ✅ | ✅ | ❌ |
| 创建 / 编辑 / 删除团队项目 | ✅ | ✅ | ❌ |
| 解散团队 | ✅ | ❌ | ❌ |
| 转让团队 | ✅ | ❌ | ❌ |
| 在项目中创建任务 | ✅ | ✅ | ✅ |
| 建任务时指派责任人 | 可指派给团队内任何人 | 同左 | 同左 |
| 编辑任务内容（标题/描述/状态/截止日期/子任务） | 任意任务 | 任意任务 | 仅自己负责的任务 |
| 删除任务 | ✅（任意） | ✅（任意） | 仅自己负责的任务 |
| 发表评论 | ✅ | ✅ | ✅ |
| 查看团队概览/项目/任务 | ✅ | ✅ | ✅ |
| 主动退出团队 | ✅（受限，见下） | ✅ | ✅ |

要点：

- **普通成员无法改动他人任务的内容**，但评论对所有团队成员开放。
- 主管视角的概览页所有成员都可见——进度透明是产品卖点；"上级看"不是一套独立权限，而是同一批数据的聚合视图。
- 主管在系统内对风险任务**没有特殊操作**（无催办、改派等按钮），了解细节靠点进任务详情。
- owner 与 admin 的区别仅在团队治理层面（解散团队、转让团队）。

## 6. 生命周期规则

- **移除成员**（owner/admin）：成员关系删除；其负责的任务**保留在原项目中**，责任人置空（未指派状态），由 owner/admin 重新指派。该用户不再能看到团队任何数据。
- **成员退出**：与被移除同等处理（任务变未指派）。**owner 不能直接退出**，必须先转让团队或解散团队。
- **删除团队项目**（owner/admin）：二次确认后硬删除，级联删除项目下全部任务、子任务、评论及相关通知。
- **解散团队**（owner）：二次确认后硬删除，级联删除团队下全部项目、任务、成员关系、邀请、通知。
- **删除个人项目**（本人）：二次确认后硬删除，级联删除项目下全部任务、子任务、评论；个人项目不产生通知。
- 个人任务（含个人项目内任务）由本人删除；个人空间本身不可删除。

## 7. 项目

项目分两类，数据模型一致（名称、描述、下属任务），区别只在归属与权限：

| | 团队项目 | 个人项目 |
|---|---|---|
| 归属 | 团队 | 本人的个人空间 |
| 创建/编辑/删除 | 团队 owner/admin | 本人 |
| 可见性 | 团队全体成员 | 仅本人 |
| 任务责任人 | 可指派给团队内任何人 | 永远是本人（无责任人概念） |
| 通知 | 按第 10 节触发 | 仅临期/逾期的自我提醒（第 10 节第 3 条同样适用）；无指派、评论、改动类通知 |
| 删除 | 二次确认后级联硬删除 | 同左 |

- 项目字段：名称、描述（可选）。
- 个人项目与团队项目相互独立；个人项目中的任务同样汇总到"我的任务"页。
- 项目内任务提供两种视图，可随时切换：
  - **列表视图**：支持按状态、截止日期筛选与排序（团队项目额外支持按责任人筛选）。
  - **看板视图**：三列——未开始 / 进行中 / 已完成；支持拖动卡片，拖动即修改任务状态。

## 8. 任务

### 字段

| 字段 | 说明 |
|---|---|
| 标题 | 必填 |
| 描述 | 可选 |
| 状态 | `todo`（未开始）/ `in_progress`（进行中）/ `done`（已完成），**手动切换**（看板拖动也是手动切换的一种） |
| 责任人 | 团队任务默认为创建者，可指派给团队内任何人；成员退出/被移除后可为空（未指派）；个人空间的任务（含个人项目内）责任人永远为自己 |
| 截止日期 | 可选；**仅日期，格式 YYYY-MM-DD** |
| 子任务 | 清单，可多条 |
| 评论 | 任务下全员可评论；个人任务的评论作为自我备注保留 |

### 子任务

- 只有两种状态：**已完成 / 未完成**（勾选框）。
- 子任务没有责任人、截止日期等独立字段。

### 状态与进度

任务状态永远手动切换，系统不因子任务完成度自动改状态；进度只用于展示与聚合。

任务进度为 0～1 的数值：

- **有子任务**：`已完成子任务数 / 子任务总数`。
- **无子任务**：按状态映射——未开始 = 0，进行中 = 0.5，已完成 = 1。

**项目进度** = 项目下所有任务进度的简单平均（每个任务等权，含未开始任务）；空项目 = 0%。团队项目与个人项目口径相同。
**团队进度** = 团队下各团队项目进度的简单平均（每个项目等权）；无项目 = 0%。个人项目不参与任何团队聚合。

`getTaskProgress` 现定义于 `packages/types/src/index.ts`；项目/团队的聚合函数在实现阶段再补充。

### 截止日期语义

- 截止日期是一个自然日，**截止日当天结束前均不算逾期；次日起算逾期**，按东八区（Asia/Shanghai）判定。
- **临期**：截止日为今天或明天且未完成（实现决定的阈值，可调整）。
- 已完成任务不再计入逾期/临期。

## 9. 页面与视图

### 9.1 认证页

- 登录、注册两个页面。

### 9.2 我的任务（登录后默认页/个人空间）

分两个区块：

1. **个人任务**：个人空间中的全部任务——无论是否归属个人项目；任务上标注所属个人项目（无项目则显示"不属于项目"）。可从此处新建个人项目、把任务归入项目。
2. **我负责的团队任务**：跨所有团队、所有项目，按责任人聚合的团队任务。

默认按截止日期排序（无截止日期排后），具体排序/筛选由实现确定。

### 9.3 团队概览（团队首页）

面向"主管视角"的只读仪表盘，所有团队成员可见：

- **项目健康度**：各项目进度条一览，按正常 / 临期 / 已逾期标色（判定依据：项目下未完成任务中是否存在逾期/临期任务，具体配色与阈值实现确定）。
- **风险区**：已逾期任务、临期任务，排在最前。
- **成员负载**：每个成员一行/一卡——进行中任务数、即将到期任务数；点入可看该成员在各项目中负责的任务。未指派任务单独显示，提示 admin 重新指派。
- 下钻路径：概览 → 项目 → 任务详情。

### 9.4 项目页（团队项目 / 个人项目通用）

- 列表/看板双视图切换（见第 7 节）。
- 有权限者（团队项目为成员、个人项目为本人）可在此新建任务。
- 个人项目页不显示责任人列/筛选与成员相关元素；项目编辑（改名/描述）、删除入口放在项目页内，仅本人可见。
- 个人项目的创建入口在个人空间侧栏与"我的任务"页头部；新建后出现在侧栏"个人项目"分组中。

### 9.5 任务详情

- 展示全部字段、子任务清单（可勾选）、评论流。
- 右侧或顶部显示责任人、截止日期、状态、进度条。
- 编辑控件按权限显隐/禁用。

### 9.6 待处理邀请

- 用户查看收到的团队邀请，接受或拒绝；团队管理员可查看/撤销发出的邀请。

## 10. 系统内通知

v1 只做系统内通知（应用内消息/未读角标），不发邮件。触发事件：

1. 收到团队邀请。
2. 被指派新任务，或任务责任人被改为自己。
3. 自己负责的任务**临期**（截止日为今天/明天）或**已逾期**。
4. 自己负责的任务收到新评论。
5. 自己负责的任务被 owner/admin 改动（内容、状态、截止日期等）。

通知至少包含：类型、接收人、关联对象（团队/项目/任务）、触发者、已读状态、创建时间。

到期/临期扫描由**定时任务**完成（实现决定：通过受保护的 Route Handler 由外部 cron/Vercel Cron 周期调用，v1 不引入独立 worker 进程）。通知的获取方式（轮询或实时）由实现确定。

## 11. 技术上下文（已定）

- Monorepo（pnpm workspaces）：`apps/web`（Next.js 16，App Router，React 19，TypeScript）、`packages/types`（共享领域模型，目前为初步骨架，需按本文档在实现阶段修订）。
- **UI：Ant Design v6**（App Router 下配 `@ant-design/nextjs-registry` 做 SSR 样式收集）+ **Tailwind CSS 4** 承担布局/微调，关闭 Tailwind preflight；中文 `zh_CN` 语言包，亮色主题，品牌色通过 Design Token 定制。
- **数据库：PostgreSQL + Drizzle ORM**；本地开发用 Docker 启动 PostgreSQL。
- 领域类型定义见 `packages/types/src/index.ts`，数据库 schema 应与之一致。

以下事项实现者可自行决定，不影响产品形态：

- 用户名/UID 的长度、字符集与随机串方案（UID 须唯一、不易枚举）

- 测试范围与分层
