# i18n 设计(中英)— 2026-11-01

状态:已与需求方对齐,待排期。本文档是排期与实现的唯一依据;实现细节中标注「builder 决定」的部分由实现者自行定夺。

## 背景与动机

项目已有真实英文用户,以「浏览」为主:看 Dashboard、看板、日历、分析、任务详情。他们自己创建内容较少,因此重点是「系统说的话」——界面文案、按钮、表单、错误提示、通知模板。用户自己输入的内容(任务标题、评论等)不在翻译范围内。

现状:全站中文硬编码,无任何集中文案层。摸底数据(2026-11-01):

- 145 个非测试源码文件含中文,约 3000 行,其中用户可见文案约 1500 行。
- features 层最重(86 个文件);共享 UI(components/,296 行)是高频复用杠杆点。
- Server Action 错误文案 ~90 处(action 层 ~38 + DomainError ~53),其中 `请先登录`/`没有权限…`/`操作失败,请稍后重试` 在 9 个 feature 里各重复一份。
- 通知文案在渲染端拼接(`notification-format.ts`,9 个 type),DB 只存 type + ID——天然利于 i18n。
- 纯数字日期 `YYYY-MM-DD` 贯穿全仓,无需翻译;中文日期文案集中在 `DueText.tsx`(今天/明天/已逾期)、`today.ts weekdayLabel`(周日…周六)、`SpaceCalendar` shortWeekDays 覆盖、`NotificationBell` 的 dayjs `fromNow()`。
- 测试是最大隐性成本:16 个 e2e 文件 720 行中文(大量用作定位器),43 个单测文件 136 处中文断言。
- `packages/types` 零文案,不涉及;无邮件、无 sitemap/robots、无 error.tsx。

## 目标

1. 全站「系统文案」支持中英切换,语言偏好账号级,登录后全局生效。
2. 历史通知在切换语言后自动以新语言渲染(不迁移数据,因为 DB 不存文案)。
3. 建立防漏翻机制:zh/en 两份 messages 的 key 集合一致性可被自动校验。
4. 把「新功能必须带 i18n」写进 `AGENTS.md`,成为后续开发的硬约定。

## 非目标

- 不翻译用户生成内容:任务标题/描述/评论、团队名、项目名、个人空间名、seed 数据。
- 不做 URL 语言前缀(`/en/space/...`),路由结构完全不动。
- 不做浏览器语言自动探测;不做顶栏快捷切换按钮(入口只在设置页)。
- 不新增 zh/en 以外的语言(架构上允许扩展,但本期不交付)。
- 不做时区/本地化口径变更:「今天」仍按 Asia/Shanghai(`todayInShanghai()`),`due_date` 仍是 Postgres `date`,日期主展示仍是 `YYYY-MM-DD`。
- 不动 `packages/types`(无可翻译内容)。

## 反目标(出现即视为失败)

- e2e 回归为「文案查表」模式,导致每加一句文案要同步维护多处测试。
- 服务端/客户端渲染不一致(antd locale 或相对时间在 hydration 时 mismatch)。
- 语言切换需要刷新整站登录态、或部分页面切换无效(语言必须是请求级一致的)。

## 需求方已决定的点

| 决定 | 结论 |
|------|------|
| 语言偏好存哪 | 账号级(users 表),登录后全局生效 |
| 默认语言 | 所有用户默认中文,不做浏览器语言探测 |
| 切换入口 | 仅设置页(个人设置),不加顶栏按钮 |
| 交付节奏 | 一期全量做完,不分批上线 |
| e2e 策略 | `data-testid` 一次性改造,不建双语对照表 |
| 英文文案 | 实现过程中由 AI 逐模块起草(先定核心术语表:空间=Space、任务=Task、项目=Project 等),全部完成后集中交需求方一次终审;不预留外审节点 |

## 技术方案

### 库选型(已定)

**next-intl ^4.14**(当前 4.14.9,peerDependencies 明确支持 Next 16 + React 19)。使用其 **without i18n routing** 模式:locale 来自 cookie,无 URL 前缀,现有路由与 `lib/routes.ts` 零改动。ICU 消息格式(插值/复数)与富文本能力开箱即用。

### locale 的来源与传递(核心机制)

1. `users` 表新增 `language` 列(`'zh' | 'en'`,默认 `'zh'`),drizzle 迁移。
2. Server Action「切换语言」:更新 DB + 写 cookie(如 `od_locale`),同事务/同请求内完成,返回后 `router.refresh()` 使 RSC 以新 locale 重渲染。
3. **DB 是唯一权威,每请求生效**(审查修正):登录后的 RSC 与 Server Action 以 `user.language` 为准(登录态请求本来就要查用户,无额外查询开销;按请求缓存防止一请求多读);cookie 只服务两个场景——未登录的 auth 路由、以及登录前的初始渲染。这样在 A 设切换后,B 设下一次请求即为新语言,不会「永远停在旧语言」。
4. 登录成功时用 DB 里的 `user.language` 重写 cookie;注册时写默认 `'zh'`。
5. 根 `layout.tsx` 的 `<html lang>` 按 locale 输出 `zh-CN` / `en-US`。
6. `providers.tsx` 保持唯一 ConfigProvider 入口,locale 按 prop 在 `zhCN`/`enUS` 间切换;`dayjs.locale` 同步切换。不违反 AGENTS.md「不得自建 ConfigProvider」。

### 翻译发生在哪一侧(已定:服务端)

- **Server Action / service 层错误在服务端翻好**再返回:`ActionResult` 结构不变(仍是 `errors: Record<field, string>`),客户端表单逻辑零改动。service 的 `DomainError` 改为携带 message key + 参数,action 层用请求 locale 翻译。
- 9 个 feature 重复的兜底文案(`请先登录`、403、`操作失败,请稍后重试`)先收敛为共享 key,再做翻译——顺序不能反。
- 页面/组件文案:RSC 用 `getTranslations`,client 组件用 `useTranslations`(经 `NextIntlClientProvider` 下发)。RSC 现在向 client 传中文 props 的地方(如 dashboard 的 `hint`),改为传 key + 参数,或 client 端直接取词。

### 通知(设计成本最高的一块)

- DB 不动,仍只存 type + ID。
- **渲染保持在客户端**(审查定案):`NotificationBell` 是 client 组件,现状就是客户端拼文案;改为 `useTranslations` 取词,通知命名空间的 messages 经 `NextIntlClientProvider` 下发(全站页面 messages 本就下发,不新增泄露面)。不做 RSC 化改造,不动 props 契约。
- 模板改 key + ICU 参数;句中粗体(如「**指派**给你」)用 next-intl 富文本 tags 能力按 tag 定位,适配各语言语序。
- 历史通知按当前语言渲染(读时翻译),无数据迁移。

### 日期与杂项

- `DueText`、`weekdayLabel`、`SpaceCalendar` 的 shortWeekDays 覆盖改为按 locale 取词;`NotificationBell` 的 `fromNow()` 跟随 dayjs locale。
- 12 个页面的 `export const metadata` 改为 `generateMetadata` + `getTranslations`。
- antd Form 的 label/message/placeholder、状态映射表(`STATUS_STYLE` 的 label 等)全部进 messages。
- 注册/登录页、not-found.tsx 一并接入。

### 测试

- **e2e(16 文件)**:为可交互元素补 `data-testid`,定位器与断言改走 testid;删除按可见文案定位的写法。不建双语表。
- **英文冒烟(审查定案)**:全量 16 条流程不复制英文版;新增一条 en 冒烟流(设置 locale cookie → 登录 → Dashboard/看板/任务详情渲染出英文关键文案)防「英文全站白屏级回归」,由 Playwright 的 locale cookie 预置实现。
- **单测**:zh locale 下文案不变的断言可保留;结构变化处(通知格式化、DomainError)改为按 key/参数断言。
- **新增**:zh/en messages key 集合一致性测试(防漏翻);语言切换 action 集成测试;getRequestConfig 的 cookie 回退测试。
- **防硬编码守卫(审查定案)**:加一个 CI 可执行的检查脚本/测试——扫描 `apps/web/src` 非测试源码中用户可见的中文字符串(排除注释、test 文件、白名单),发现即失败。没有它,key 一致性测试只能防「漏翻」,防不了「绕过 messages 直接写中文」。
- 现有约定不变:Vitest 串行、跑 DB 用例前 source env。

### 交付顺序建议(排期参考)

1. 基建:`users.language` 迁移 → cookie + next-intl 接线 → providers/html lang → 设置页切换 → key 一致性测试。
2. 共享 UI(`components/ui` + auth 页)。
3. features 各模块组件(teams → personal → dashboard/kanban/calendar/analysis → notifications)。
4. service/action 错误码收敛 + 服务端翻译。
5. 通知格式化富文本改造。
6. metadata 与遗漏项。
7. e2e data-testid 改造。
8. `AGENTS.md` 增补 i18n 约定(新功能必须带 i18n、文案必须进 messages、禁止硬编码用户可见中文)。

每步之后 `pnpm typecheck && pnpm test` 保持全绿,e2e 在第 7 步前允许中文断言(此时 UI 已双语,断言按默认 zh 仍成立)。

## 约束(实现必须遵守)

- `docs/V1_TASKS.md` 冻结契约不得修改(`AppShell`、`(dashboard)/layout.tsx` 导入关系);`providers.tsx` 是允许修改的既有全局入口。
- UI 视觉对照 `docs/prototypes/`,本次不改布局、只换文案来源;中文渲染结果必须与现状逐字一致(messages zh 文案从现有代码原样搬运)。
- antd v6 组件优先,Tailwind 只做布局;不加 preflight。
- 时区/日期口径不变(Asia/Shanghai)。
- next 相关写法遵守 `apps/web/AGENTS.md`,先读 `node_modules/next/dist/docs` 相关章节。

## 留给 builder 决定的点

- messages 文件组织:单文件 vs 按命名空间拆分;TS key 类型如何生成(next-intl 的 `AppConfig` 声明)。
- `DomainError` 改造签名:key + params 的具体形态,以及与现有 `toFailure()` 的衔接。
- 通知富文本:next-intl tags 与现有 `{parts: [{text, bold}]}` 结构的对接方式。
- `data-testid` 命名约定与补齐范围(以 e2e 用到的元素为准)。
- 设置页语言切换的具体 UI(antd Select 即可,对照原型设置页风格,不改布局)。
