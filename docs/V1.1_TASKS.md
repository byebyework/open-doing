# Open Doing v1.1 任务板(草案)

日期:2026-10-27
依据:[2026-10-21-open-doing-v1-design.md](./2026-10-21-open-doing-v1-design.md)、[ARCHITECTURE.md](./ARCHITECTURE.md)、[V1_TASKS.md](./V1_TASKS.md)、2026-10-26 功能符合性审核

**本文件性质**:v1.1 的**粗粒度 todolist**,只圈范围与依赖,不定细节。每条任务在**开工当天与负责人讨论定稿**(形态、文案、交互、数据口径都留白),讨论结论回填到对应任务的「已定」小节。任务拆分、验收标准与文件目录分配在讨论时细化。

**已裁决的方向**(2026-10-27,与产品负责人确认):

1. 团队加入改为**双向模型**:保留 owner/admin 按 UID 定向邀请(v1 现状),新增**成员凭团队加入码申请加入**(正向加入),由 owner/admin 审批。
2. 空间切换后默认提供五大模块:**Dashboard / Kanban / Analysis / Calendar / Zone Setting**,个人空间与团队空间两套上下文都要有。

## 1. 范围外(明确不做)

- v1 全部功能的行为变更(除下方任务触及的部分);
- 公开 REST API、邮箱注册、密码找回(沿用 v1 约束,见 V1_TASKS §2 全局约束);
- 实时协作/推送(继续轮询或 Server Action 刷新)。

### S1 正向加入模型设计讨论稿

加入码(tid)与申请-审批流的完整规则定稿。**待讨论**(已知开放点,讨论时增删):

- 加入码形态与承载:独立 `tid`(如 `team_xxxxxx`?是否用与 UID 同族的 `doing_` 前缀)还是复用/扩展 slug?码是否可重置、可关闭(「禁止凭码加入」开关)?
- 申请流状态机:`pending → approved / declined / cancelled / expired`?同一人对同一团队的重复申请约束;主动退出后凭码再申请的处理。
- 审批人:owner/admin;是否允许 admin 之外的角色;批量审批是否需要。
- 容量与防滥用:单团队人数上限?申请频率限制?
- 通知接入:新通知类型(申请产生 → 审批人;结果产生 → 申请人),复用同事务写入与 cron 体系。
- 与 v1 定向邀请的关系:两入口并存时的文案与入口布局。

**已定**(2026-10-27,与产品负责人确认;实现计划见 `docs/superpowers/plans/2026-10-27-join-by-code-and-space-switcher.md`):

- **加入码**:`teams.join_code`,8 位无前缀随机码,字符集 `23456789ABCDEFGHJKMNPQRSTUVWXYZ`(去 I/L/O 的 31 字符表,31^8 不可枚举);`teams.join_code_enabled` 开关(默认开,关闭后凭码申请报「未开放」);owner/admin 可重置(重置即换码)。不复用 slug。
- **状态机**:`pending → approved / declined / cancelled`(申请人可取消);**无 expired**(不引入 cron);部分唯一索引 `(team_id, user_id) WHERE status='pending'`;被拒/退出后**可再申请,不限频**;已是成员申请返回幂等错误。
- **审批**:owner/admin,复用现有权限动作 `team:invite`(不新增权限名);不批量;approve 同事务建 membership(member)+ 写通知。
- **容量**:不设上限(与 v1 邀请一致)。
- **通知**:`NotificationType` 新增 `team_join_requested`(→ 全体 owner/admin)/ `team_join_approved` / `team_join_declined`(→ 申请人),同事务写入;共享契约变更按 §4 记录。

### S3 凭码申请与审批的 UI 全流程

申请人侧:凭码申请入口(位置待定:登录后独立页 or 空间切换器内?)、我的申请状态;审批人侧:团队设置内的申请队列(批准/拒绝);通知中心新类型的展示与跳转。对照 `docs/prototypes/` 风格补原型页。文案与空态在开工时定。

**已定**(2026-10-27):

- 申请人侧:独立页 `/teams/join`(RSC + client 表单,静态段优先级高于 `[teamSlug]` 动态段,无路由冲突);入口在 SpaceSwitcher 菜单「凭码加入团队」+ `/teams/new` 页互链。
- 「我的加入申请」并入 `/invites` 页新区块(pending 可取消,取消走 ConfirmModal;approved/declined 展示结果 tag)。
- 审批人侧:团队设置页新增「凭码加入」区块(码展示可复制 + 重置 ConfirmModal + 开关 Switch)与「加入申请」区块(逐条批准/拒绝,拒绝走 ConfirmModal)。
- 文案:申请成功 toast「申请已提交，等待管理员审批」;加入页说明「输入团队加入码，提交后由团队管理员审批」,页尾「不知道加入码？向团队管理员索取，或创建自己的团队」;`/teams/new` 页尾互链「已有加入码？凭码加入」;`/invites` 区块标题「我的加入申请（N）」。
- 空态与结果:无申请时一行「还没有加入申请，可在 凭码加入团队 页提交。」(带链接);结果 tag approved「已通过」绿 / declined「未通过」灰 / cancelled「已取消」灰(取消项保留展示,避免计数与条目不一致)。
- 实现期微调(2026-10-27):SpaceSwitcher 菜单项实际文案为「凭码加入」;`/teams/join` 表单辅助文案「向团队管理员索取 8 位加入码；提交后可在「待处理邀请」页查看审批进度。」

### M1 五模块信息架构与路由方案(讨论稿)

确定五大模块在个人/团队两个空间下的统一 IA、路由结构与导航形态。**待讨论**:

- 模块×空间矩阵:每个模块在两个空间下是否都存在、差异是什么(如 Analysis 在个人空间是否有意义)。
- 路由方案:与 S4 的空间 URL 决策合并定稿;现有页面(`/my`、团队概览、项目页)如何映射/迁移/重定向。
- 导航形态:侧栏分组改造?空间内二级导航(tab)?移动端导航方案(现状 <861px 无导航,必须一并解决)。
- 各模块最小可用范围(v1.1 做到什么程度算完,防止范围膨胀)。

**已定**(2026-10-28,与产品负责人确认):

- **模块×空间矩阵**:五个模块在两个空间**都存在**,差异在内容侧重而非存在性(个人 Analysis 做轻量版:完成趋势/拖延统计;团队 Analysis 做完整版:吞吐/负载/健康度)。各页具体差异留到 M2–M5 开工时定。
- **路由方案(统一空间树,替换 v1 双树)**:`/space/{spaceRef}/{module}`,`spaceRef` 取 `personal` 或团队 slug;`module` ∈ `dashboard / kanban / calendar / analysis / settings`(Zone Setting 用 `settings`,最终命名 M6 敲定)。设计依据:领域模型中「空间」是一等公民,个人/团队是同一抽象的两个实例,路由镜像领域模型;双树是 v1 历史产物,不再加盖。每个模块页面一份路由壳,组件层个人/团队共用。
- **旧 URL 重定向**:`/my/*` → `/space/personal/*`;`/teams/{slug}/*` → `/space/{slug}/*`;项目页与任务详情映射到新结构(`/space/{ref}/projects/{slug}`,任务详情保持不透明 ID,具体挂法 M2 定)。非空间页 `/teams/new`、`/teams/join`、`/invites` 保持独立路由(是否归整为同级位置写稿时定)。
- **导航形态**:桌面侧栏 = 空间切换器(S4 实装的 SpaceSwitcher 换数据源)+ 当前空间五模块主菜单;「我的任务/团队概览/项目列表」等内容归入各模块页面内部。移动端(<861px,沿用现有断点)顶栏汉堡按钮唤出 **Drawer**,与桌面共用同一棵导航树,解决现状移动端无导航缺口;底部 Tab Bar 不做(真实使用确认高频动线后再议)。
- **URL 状态约定**:模块内筛选/排序/视图状态进 URL query(清 §3 对应债务);侧栏模块高亮由路由段直接推导。
- **各模块 v1.1 最小可用范围**:
  - M2 Dashboard:个人 = 今天任务(可勾选)+ 逾期/临期风险区 + 统计卡(总数/本周截止);团队 = 项目进度条列表 + 重要节点(最近截止)+ 成员负载简表;复用现有组件,口径沿用 v1。
  - M3 Kanban:空间级聚合看板,`todo/in_progress/done` 三列,卡片标项目归属,按项目筛选,拖拽改状态复用现有实现;不做泳道、不做按负责人分组。
  - M4 Calendar:月视图为主 + 列表式周视图,逾期/今天/临期着色 + 「还有 N 天」倒计时,点击进详情;无 `due_date` 任务不进日历(留说明入口);**只读**,不做拖拽改期;antd Calendar 二次封装 vs 自绘,M4 开工选型。
  - M5 Analysis:只读聚合页,默认近 30 天可切换;个人 = 完成趋势 + 逾期/拖延统计,团队 = 吞吐 + 成员负载 + 项目健康度;引入新图表依赖前先讨论。
  - M6 Zone Setting:个人设置页建壳,内容 M6 开工定;团队设置已由 S3 基本对齐。

个人空间仪表盘(现有 `/my` 聚合升格)与团队概览对齐同一 IA;统计卡、风险区、成员负载复用现有组件。数据口径沿用 v1(Asia/Shanghai、简单平均)。

**已定**(2026-10-28,与产品负责人确认;原型先行——先在 `docs/prototypes/` 出原型页审核通过后再写实现计划):

- **Dashboard 轻量化分工**:Dashboard 只做「今天 + 风险」,全量任务浏览归 M3 Kanban;「我的任务」页的全量列表不再保留,未指派区精简为计数+入口(完整列表归 Kanban)。
- **今天列表口径**:未完成且 `due_date ≤ 今天` 的全部任务(个人任务 + 指派给自己的团队任务),逾期置顶按截止升序,上限 20 条 + 页尾「查看全部」跳 Kanban;团队任务项带团队名标签,链接进对应任务详情。风险区并入该列表(逾期项天然置顶),不单独成区。
- **行内勾选完成**:个人任务直接勾;指派给自己的团队任务也可勾(assignee 本人满足 `canEditTask`),走现有团队任务状态流转 Action,乐观更新。
- **个人 Dashboard 形态**:统计卡沿用四张(进行中/今日明日到期/已逾期/本周已完成)+ 今天任务列表;保留新建任务/新建项目按钮。

- **原型产出**:`docs/prototypes/space-dashboard-personal.html` 与 `space-dashboard-team.html`,沿用现有设计令牌与 README 约定。

### M3 空间级 Kanban

跨项目聚合的空间级看板:个人空间聚合全部个人任务;团队空间聚合本团队全部任务(含未指派)。复用 `PersonalKanban`/`TeamKanban` 的拖拽、乐观更新与窄屏降级策略;需解决跨项目拖拽时的项目归属展示与筛选。数据聚合走 SQL 侧,不整表拉内存。

**已定**(2026-10-28,与产品负责人确认;原型先行——先在 `docs/prototypes/` 出原型页审核通过后再写实现计划):

- **定位**:看板 = 全局任务状态全景(Dashboard 管「今天该干嘛」,Kanban 管「全局都在哪」)。三列 `todo/in_progress/done`,卡片跨项目聚合(个人空间 = 全部个人任务;团队空间 = 本团队全部任务,含未指派)。
- **卡片信息**:标题 + 项目归属 tag(团队 = 品牌紫浅底 / 个人 = 薄荷浅底,与 Dashboard 今天列表同套)+ 截止日期(逾期红 / 今天黄,无截止不显示)+ 负责人(团队空间;未指派显式标「未指派」)+ 子任务进度小字;卡片不重复状态 tag(列即状态)。
- **列头**:三列各计数;待办/进行中列头附逾期计数(红色小字);done 列头显示本周完成计数。
- **列内排序**:逾期置顶按截止升序,其余按截止升序,无截止垫底(与 Dashboard 今天列表同口径)。
- **筛选**:按项目单选(「全部」+ 各项目),状态进 URL query(执行 M1 URL 状态约定);团队空间额外有「未指派」筛选项。
- **拖拽**:只改状态、不改项目归属;权限沿用 `canEditTask`,复用现有乐观更新、失败回滚与窄屏降级。
- **done 收敛**:done 列默认只显示最近 7 天完成的任务,尾部一行「更早 N 项已完成,已在各项目归档」提示;其余两列不设限。
- **不做**:泳道、按负责人分组、WIP 限制、看板内直接指派(指派引导进任务详情)。
- **留白**(原型/实现时定):URL query 参数命名、空态文案、列头计数在窄屏的呈现。
